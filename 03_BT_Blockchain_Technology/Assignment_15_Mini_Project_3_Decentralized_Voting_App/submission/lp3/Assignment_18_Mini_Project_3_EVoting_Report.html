Title of the Assignment:

Design and Development of a Decentralized E-Voting System (dApp) using Ethereum Blockchain, Solidity Smart Contracts, and Web3 / MERN Stack.

Objective of the Assignment:

  • To design and deploy a tamper-proof, transparent smart contract in Solidity for conducting democratic elections.
  • To eliminate traditional centralized electronic voting vulnerabilities: single points of failure, ballot stuffing, unauthorized voting, and centralized database tampering.
  • To integrate MetaMask browser wallet extension via Web3.js for cryptographic signature verification and voter authorization.
  • To enforce mathematical double-voting prevention using EVM state mappings and the Checks-Effects-Interactions pattern.
  • To test, migrate, and evaluate contract execution on a local Ethereum blockchain environment (Ganache).

Prerequisites:

  • Basic knowledge of Blockchain, Peer-to-Peer networks, Distributed Ledgers, and EVM (Ethereum Virtual Machine).
  • Fundamentals of Cryptography: Public/Private Key pairs, SHA-256 / Keccak-256 hashing, and digital signatures.
  • Programming in Solidity, JavaScript, Node.js, and React.js.
  • MetaMask wallet extension and Truffle Suite (Truffle CLI & Ganache).

1. Theoretical Background

1.1 Limitations of Centralized Voting: Conventional electronic voting machines (EVMs) and centralized cloud-hosted voting portals store ballot tallies on private SQL/NoSQL databases controlled by central authorities. These architectures suffer from insider manipulation, lack of public verification, vulnerability to cyberattacks, and non-transparent vote aggregation.

1.2 Blockchain Solutions: A decentralized application (dApp) solves these challenges through:

  • Immutability: Once a vote transaction is mined into an Ethereum block, it cannot be edited, deleted, or reversed.
  • Decentralization: The election state is maintained across all participating peer nodes; no single party can alter the results.
  • Cryptographic Proof of Single Vote: The smart contract uses an Ethereum account mapping mapping(address => bool) public voters. Each address can cast exactly one vote; duplicate attempts trigger an EVM revert.
  • Pseudonymous Transparency: Public keys ensure accountability without revealing real-world identity on-chain.

3. Smart Contract Source Code (Election.sol)

pragma solidity ^0.5.16; contract Election { // Model a Candidate struct Candidate { uint id; string name; uint voteCount; string details; string election_id; } // Store accounts that have voted (Address => True/False) mapping(address => bool) public voters; // Store and fetch Candidates by numeric ID mapping(uint => Candidate) public candidates; // Count of registered candidates uint public candidatesCount; // Constructor constructor() public {} // Voted event emitted on every valid transaction event votedEvent( uint indexed _candidateId ); // Add Candidate function function addCandidate(string memory _name, string memory _details, string memory _election_id) public { candidatesCount++; candidates[candidatesCount] = Candidate(candidatesCount, _name, 0, _details, _election_id); } // Cast Vote function with double-voting prevention function vote(uint _candidateId) public { // Constraint 1: Check that voter has not voted before require(!voters[msg.sender], "Voter has already voted."); // Constraint 2: Verify candidate ID exists require(_candidateId > 0 && _candidateId <= candidatesCount, "Invalid candidate."); // Effects: Mark voter address as true voters[msg.sender] = true; // Effects: Increment vote count candidates[_candidateId].voteCount++; // Interactions: Emit event to blockchain receipt emit votedEvent(_candidateId); } }

    cd E-Voting-App/blockchain
    truffle compile
    truffle migrate --reset
  3. Step 3: Setup MetaMask: Connect browser to Custom RPC http://127.0.0.1:7545 and import Ganache accounts using private keys.
  4. Step 4: Launch Backend & Frontend Servers:
    # In server directory:
    cd E-Voting-App/server && npm run dev

    # In blockchain frontend directory:
    cd E-Voting-App/blockchain && npm start
  5. Step 5: Admin & Voter Operations:
    • Admin logs in and registers candidates with election metadata.
    • Voters log in, authenticate MetaMask, select candidate, and click Vote.
    • MetaMask opens prompt displaying Gas Limit and Gas Fee; voter confirms transaction.
    • Smart contract mines transaction, increments candidate vote count, and records voter address.

7. Viva-Voce Questions & Answers

Q1. What is the role of the Ethereum Virtual Machine (EVM) in this dApp? The EVM acts as the decentralized computational runtime environment that executes the compiled Solidity bytecode across every full node in the Ethereum network, guaranteeing deterministic state transitions.
Q2. How is double-voting mathematically prevented in Election.sol? Double-voting is prevented by the mapping mapping(address => bool) public voters;. When a vote is cast, require(!voters[msg.sender]) ensures the sender's address hasn't been flagged. Once executed, voters[msg.sender] = true locks the account from voting again.
Q3. What is the difference between call() and send() methods in Web3.js? call() is a read-only operation executed locally on the client node without consuming gas or modifying blockchain state. send() creates a state-changing transaction that consumes gas, requires cryptographic signing, and must be mined into a block.
Q4. Why are Events used in Solidity (e.g., votedEvent)? Events write lightweight logs to transaction receipts on the blockchain. They allow external client applications (like our React frontend) to listen for state changes and update the UI asynchronously without continuously polling storage.
Q5. What are the key advantages of using Truffle and Ganache for development? Truffle automates contract compilation, linking, and deployment via migrations, and provides an automated testing framework. Ganache provides a personal, deterministic local blockchain with instant mining and pre-allocated accounts for rapid debugging.
Q6. How does blockchain guarantee that election results cannot be hacked or altered? Every block contains the cryptographic hash of the previous block, creating an immutable chain. Modifying any vote would change the block's Merkle root and hash, invalidating all subsequent blocks across all nodes according to the consensus protocol.
